# A/B Test Plan

## Цель

Сравнить две версии модели прогнозирования дефолта:

- **v1** — текущая production-модель;
- **v2** — новая версия модели с обновлёнными параметрами или признаками.

## Разделение трафика

Трафик делится случайным образом в пропорции 50/50:
- 50% запросов направляется на модель v1;
- 50% запросов направляется на модель v2.

Разделение можно выполнять по `client_id` с помощью детерминированного хеширования.

## Длительность

Предварительная длительность A/B-теста: **2–4 недели**, либо до достижения необходимого объёма выборки.

## Основная метрика

- **F1-score** для класса дефолта.

F1-score выбран как основная метрика, так как он балансирует precision и recall в задаче обнаружения дефолтов.

## Дополнительные метрики

- **Precision** — важна, если бизнес хочет снизить число ложных отказов хорошим клиентам.
- **Recall** — важна, если бизнес хочет уменьшить число пропущенных дефолтов.

## Бизнес-метрики

- **Expected loss reduction** — снижение ожидаемых финансовых потерь.
- **Approval rate at fixed risk** — доля одобренных заявок при фиксированном допустимом уровне риска.

## Статистический анализ

Для анализа результатов могут использоваться:
- доверительные интервалы для разницы метрик между v1 и v2;
- z-test для сравнения долей;
- bootstrap для оценки устойчивости различий.

Уровень значимости: **alpha = 0.05**.

## Критерий успеха

Новая модель v2 считается успешной, если:
- показывает улучшение основной метрики F1-score;
- не ухудшает критически precision/recall;
- улучшает хотя бы одну из бизнес-метрик.

## Связь с архитектурой

Для поддержки A/B-теста сервис должен уметь:
- маршрутизировать запросы между двумя версиями модели;
- логировать, какая версия модели выдала предсказание;
- сохранять результаты для последующего анализа.
